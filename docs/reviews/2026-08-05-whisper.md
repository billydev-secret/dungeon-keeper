# Whisper — battery review, 2026-08-05

Bundle: `cogs/whisper_cog.py` (2,660), `whisper/{logic,embeds}.py`,
`services/whisper_{service,repo,models}.py`, panels `config-whisper.js`,
`mod-whisper-audit.js`, route `moderation.py:1206`. Spec: `whisper_spec.md`.
Prod: 564 whispers, 295 replies.

## Architecture

- Clean four-layer split (cog I/O → embeds → logic/service pure → repo).
  Repo cascades are real FKs (`ON DELETE CASCADE` on guesses/replies/reports/
  reply_reports) — deletion correctness lives in the schema, good.
- **A1 — forget-me over-deletes across guilds** (`whisper_cog.py:2119-2126`):
  the orphan-reply cleanup `DELETE FROM whisper_replies WHERE from_user_id=?`
  (and `to_user_id`) has **no guild scoping** — `whisper_replies` has no
  guild column, so scoping requires a join through `whispers`. Prod has two
  guilds; `/whisper forget-me` in guild B silently destroys the user's reply
  history in guild A. The command's own copy says "for this server".
  Fix: `DELETE FROM whisper_replies WHERE from_user_id=? AND whisper_id IN
  (SELECT id FROM whispers WHERE guild_id=?)` — but note those parent
  whispers were just deleted, so the *orphan* case only exists for replies
  whose parent went via the other party's forget-me; the subquery must run
  **before** the whisper deletes, or accept cascade handles in-guild rows and
  the orphan sweep should filter by… simplest correct order: capture the
  guild's whisper ids first, then delete. **Priority: high** (destroys
  another guild's data on a single-guild request) + regression test at repo
  layer reproducing the two-guild state.
- **A2 — dead code**: `decrement_guesses_left` (repo:158) is superseded by
  `try_consume_guess`; only a unit test and a stale docstring reference it.
  /simplify candidate: delete fn + test, fix `whisper_service.py:134`
  docstring. Not applied in this pass (batched with A1's repo edit).
- Tests: 103 fns in `test_whisper_logic.py` + repo tests under
  `tests/unit/`. Coverage shape is right; A1 shows the *multi-guild* state
  was never in a fixture — add it.
- The no-contact gate's identical-confirmation constant
  (`whisper_service.py` SENT_CONFIRMATION comment) is a genuinely good
  pattern — cite it in the synthesis as a house standard.

## GDPR

- **This is the model feature** for the register's "deliberate preserve"
  column: real opt-in consent view (role granted only on Confirm), per-user
  self-service erasure (`/whisper forget-me`), content never exposed on the
  dashboard (audit route returns ids/state only — verified moderation.py:
  1237-1247; snowflakes as strings ✓), sender identity admin-gated, and the
  spec discloses that admins can deanonymize.
- G1: **retention is indefinite** — whispers age-lock at 30 days but rows
  live forever. Register decision: preserve (forensic) is defensible since
  reports must stay actionable, but a 12-month hard-delete sweep for
  never-reported whispers would be better minimization. → Ben.
- G2: mod-log channel fan-out includes whisper **content** + sender id
  (embeds.py build; spec discloses). Prod check: `whisper_log_channel_id`
  — verify configured target is a mod-only channel (can't verify
  channel perms from here; flag for live QA).
- G3: `purge_user_data` does not cover whisper tables — but forget-me is the
  per-feature erasure path, so the register marks whisper **decided:
  self-service erase + deliberate audit preserve**, pending A1 fix and the
  D1 reporter-rows decision.

## Verdict

paper cuts (A2 dead code, D1 spec drift). GDPR posture is the strongest in
